We designed, verified and evaluated a five-stage pipelined RV32I processor in Verilog
HDL, together with a single-cycle baseline, an assembler, six benchmark programs and a
synthesis and performance analysis flow. The pipeline resolves data hazards by forwarding
and a one-cycle load-use stall, and control hazards by flushing two instructions on a taken
branch or jump. All unit testbenches pass, the six system programs and the six benchmarks pass on
both designs, and a differential test confirms that the pipeline and the baseline end with
identical registers and data memory on all twelve programs.

The measurements give a clear picture of what pipelining buys. On the six benchmarks the
pipeline needs 1.40 to 1.58 cycles per instruction, 1.48 over all benchmarks together, and
every run matches $C = N + 4 + S + 2T$. Taken branches and jumps cause most of the lost
cycles: in the benchmarks the flush cycles $2T$ make up 87\,\% of the stall and flush
cycles. In return the clock is faster. On a Lattice ECP5 LFE5U-85F the pipeline reaches
56.55~MHz against 28.43~MHz for the single-cycle design, 1.99 times, and uses 3300 logic
cells against 7392, because the single-cycle data memory has no register behind it and is
built from lookup tables. The net result is a speed-up of 1.26 to 1.43 times on the
benchmarks. This is well below the factor of five that the number of stages suggests,
since both the clock gain (1.99) and the cycle ratio (0.63 to 0.72) fall short of the ideal.
Very short programs gain nothing: the load-use and branch test programs of five and eleven
instructions run at 0.99 and 0.95 times the baseline speed, because the four fill cycles and
the flushes dominate.

These results hold within clear limits. The processor implements only 29 instructions with
word-sized loads and stores, uses static predict-not-taken branching, has no cache and no
exceptions, and was run on programs of at most 1231 instructions. The maximum frequencies
come from place and route of an open-source flow for one FPGA device and one placement seed,
not from silicon or a board.

Future work follows from the data. A branch predictor would attack the largest source of
lost cycles, the taken-branch flushes. Byte and half-word loads and stores, a cache and
longer benchmarks would make the comparison closer to a practical processor, and
implementing the design on an FPGA board would confirm the timing results.
